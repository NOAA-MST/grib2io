# FAIR metadata in grib2io Kerchunk reference manifests

This directory demonstrates the FAIR metadata added to Kerchunk reference
manifests generated by `grib2io.kerchunk.ReferenceGenerator`.

A Kerchunk manifest is a JSON index that maps Zarr chunk keys to byte ranges in
the original GRIB2 files. It lets a client open a collection of GRIB2 messages
as a virtual Zarr store and read only the bytes it needs, without converting or
copying the data. What it does *not* do, by default, is carry any description of
what the data is — that lived only in the filename and the directory path.

The work here adds that description to the manifest itself, following the
[FAIR principles](https://www.go-fair.org/fair-principles/) (Findable,
Accessible, Interoperable, Reusable) and the
[CF conventions](https://cfconventions.org/).

## Motivation

Before this change, a manifest separated from its filename was unidentifiable.
The refs went straight from `.zgroup` into the variable arrays, so nothing in
the file recorded which model produced it, which center ran it, which cycle it
came from, or which GRIB2 table versions applied. Two manifests sitting side by
side in a directory were distinguishable only by their names.

Variable-level metadata was similarly thin. Each array carried the GRIB2-native
codes — `discipline`, `parameterCategory`, `parameterNumber` — which are precise
but require a GRIB2 table lookup to interpret. A user searching for temperature
had to know that NCEP calls it `TMP`; a CF-aware tool looking for
`air_temperature` found nothing.

The consequence is practical rather than theoretical. Manifests are meant to be
published and consumed by people who did not generate them, often through
tooling that speaks CF rather than GRIB2. Metadata that only exists in a file
path does not survive that journey.

## What changed

### New: root-level dataset metadata

The generator now writes a root `.zattrs` block describing the dataset as a
whole, decoded from GRIB2 Sections 0, 1, and 4 of a representative message:

```json
{
  "Conventions": "CF-1.8",
  "institution": "US National Weather Service - NCEP",
  "source": "Analysis from GFS (Global Forecast System)",
  "reference_time": "2026-08-10T00:00:00",
  "reference_time_significance": "Start of Forecast",
  "production_status": "Operational Products",
  "type_of_data": "Forecast Products",
  "GRIB2_master_table_version": 2,
  "GRIB2_local_table_version": 1,
  "grib2io_version": "2.8.1"
}
```

These survive into `ds.attrs` when the manifest is opened with xarray, so the
provenance travels with the data rather than with the filename.

### Enriched: per-variable metadata

Each variable array gains CF vocabulary alongside the GRIB2-native keys, which
are retained:

```json
{
  "_ARRAY_DIMENSIONS": ["valid_time", "isobaric_surface", "y", "x"],
  "coordinates": "latitude longitude",
  "standard_name": "air_temperature",
  "long_name": "Temperature",
  "units": "K",
  "discipline": 0,
  "parameterCategory": 0,
  "parameterNumber": 0,
  "typeOfFirstFixedSurface": 100,
  "shortName": "TMP",
  "valid_time": "2026-08-10T00:00:00",
  "lead_time_hours": 0.0
}
```

Keeping both vocabularies matters: CF makes the data interoperable, while the
GRIB2 codes make it reproducible back to the source message.

## Field reference

### Root `.zattrs`

| Key | Source | Description |
|---|---|---|
| `Conventions` | fixed | `CF-1.8` |
| `institution` | Section 1 | Originating center, with sub-center appended when defined |
| `source` | Section 4 | Generating process (model name) |
| `reference_time` | Section 1 | Model cycle, ISO 8601 |
| `reference_time_significance` | Section 1 | Usually "Start of Forecast" |
| `production_status` | Section 1 | Operational, test, research, etc. |
| `type_of_data` | Section 1 | Analysis, forecast, control, perturbed, etc. |
| `GRIB2_master_table_version` | Section 1 | Numeric code |
| `GRIB2_local_table_version` | Section 1 | Numeric code |
| `grib2io_version` | runtime | Version that produced the manifest |

### Variable `.zattrs` (new / changed keys)

| Key | Description |
|---|---|
| `standard_name` | CF standard name via the `shortname_to_cf` table; `"unknown"` when the table has no entry for the parameter |
| `long_name` | Human-readable parameter name (`msg.fullName`) |
| `units` | Parameter units |
| `cell_methods` | CF cell methods, only where the parameter defines one (e.g. `time: sum` for accumulations) |
| `lead_time_hours` | Forecast lead time in hours |
| `duration_hours` | Statistical processing period, only where one applies |
| `level` | Human-readable level/layer string (`"500 mb"`, `"2 m above ground"`), from the `Level` descriptor. Present only on single-level variables — see note below. |
| `valueOfFirstFixedSurface` | Numeric level value in the units of `typeOfFirstFixedSurface`. Present only on single-level variables. |

### Level metadata: variables vs. coordinates

A variable that spans several levels cannot be described by one level string, so
`level` and `valueOfFirstFixedSurface` are written only when the variable holds a
single level. For multi-level variables the values live on the vertical
coordinate instead, which carries CF metadata of its own:

| Key | Description |
|---|---|
| `units` | From GRIB2 Table 4.5 (`Pa` for isobaric, `m` for heights and depths). Omitted where the table gives "unknown", as it does for single-valued surfaces. |
| `standard_name` | CF name where one applies — `air_pressure`, `height`, `depth`. Parametric coordinates (sigma, hybrid) are omitted: their CF names require `formula_terms`, which a manifest does not carry. |
| `positive` | `"up"` or `"down"`, so a consumer can orient the axis. |
| `long_name` | Surface description from Table 4.5. |
| `typeOfFirstFixedSurface` | The GRIB2 code, retained alongside the CF vocabulary. |

```python
ds["TMP"].attrs.get("level")            # -> None (41 pressure levels)
ds["isobaric_surface"].attrs["units"]   # -> 'Pa'
ds["PRMSL"].attrs["level"]              # -> 'mean sea level'
```

Where two variables need different values for the same dimension — different
pressure-level sets, percentile counts, or accumulation windows — the second gets
a numbered suffix (`isobaric_surface_2`, `percentileValue_2`). Without that they
would overwrite each other's coordinate array and the manifest would not open.

## Setup: install this branch

The Kerchunk codec requires a compiled `grib2io` build, so this is an editable
install from source rather than a wheel.

```bash
# 1. Get the code and check out the feature branch
git clone https://github.com/NOAA-MST/grib2io.git
cd grib2io
git checkout feature/kerchunk-fair-metadata

# 2. Create an environment with the compiled build dependencies
conda create -n grib2io-fair -c conda-forge python=3.12 g2c ip cmake compilers -y
conda activate grib2io-fair

# 3. Install this checkout in editable mode with the extras used here.
#    - kerchunk : reference generation (kerchunk, numcodecs, fsspec)
#    - xarray   : opening a manifest as a virtual Zarr store
G2C_DIR=$CONDA_PREFIX IP_DIR=$CONDA_PREFIX \
  pip install -e '.[kerchunk,xarray]'
```

Verify the install and codec registration:

```bash
python -c "from grib2io.kerchunk import ReferenceGenerator; import grib2io.codecs; print('ok')"
```

## How to generate a manifest

**Command line:**

```bash
grib2io kerchunk gfs.t00z.pgrb2.0p25.f000 --output gfs_references.json
```

**Python API:**

```python
from grib2io.kerchunk import ReferenceGenerator

gen = ReferenceGenerator("gfs.t00z.pgrb2.0p25.f000.conus.grib2")
gen.generate()
gen.to_json("gfs_references.json")
```

`ReferenceGenerator` also accepts a list of files, message `filters=`, and
remote URIs / `storage_options=` for scanning objects on S3 or HTTP.

## How to open a manifest

```python
import fsspec, xarray as xr
import grib2io.codecs           # registers the grib2io Zarr codec

fs = fsspec.filesystem("reference", fo="gfs_references.json", remote_protocol="file")
ds = xr.open_dataset(fs.get_mapper(""), engine="zarr", consolidated=False)

print(ds.attrs["institution"])          # -> US National Weather Service - NCEP
print(ds["HGT"].attrs["standard_name"]) # -> geopotential_height
```

`remote_protocol` should match where the referenced GRIB2 bytes live
(`"file"` for the local examples here, `"s3"` / `"http"` for remote sources).

## Validating a manifest

`check_manifests.py` runs a fixed set of checks against one or more manifests,
so a newly supported model can be validated in one command:

```bash
python check_manifests.py gfs_references.json nam_references.json
```

It reports on root metadata completeness, CF coverage across data variables, the
single/multi-level attribute split, level coordinate metadata, the grid
definition, and whether every variable's shape agrees with the coordinate arrays
it references. Unless `--no-read` is given it also opens each manifest with
xarray and performs one byte-range read, which is the only check that needs the
`grib2io` codec and access to the referenced GRIB2 bytes.

The exit status is non-zero if any check fails, so it can gate a generation run:

```bash
grib2io kerchunk "$src" --output "$out" && python check_manifests.py "$out"
```

Note that `ReferenceGenerator` already validates shape/coordinate consistency
itself and raises before writing; pass `validate=False` to skip that. This
script re-checks it alongside the metadata expectations.

## Example files in this directory

Both manifests were generated with this feature branch from small CONUS
sub-region subsets pulled from [NOMADS](https://nomads.ncep.noaa.gov), cycle
`2026-08-10 00Z`. The subsets contain HGT/TMP/UGRD/VGRD at 500 mb, 850 mb,
surface, and 2 m — enough to show multiple levels, surfaces, and grid types.

| File | Source | Grid | Notes |
|---|---|---|---|
| `data/gfs.t00z.pgrb2.0p25.f000.conus.grib2` | GFS 0.25° analysis | regular lat/lon (GDT 3.0), 61×61 | |
| `gfs_references.json` | ↑ | | Manifest for the GFS subset. |
| `data/nam.t00z.awphys00.tm00.conus.grib2` | NAM 12 km | Lambert conformal (GDT 3.30), 150×123 | Contrasting projected grid. |
| `nam_references.json` | ↑ | | Manifest for the NAM subset. |
| `check_manifests.py` | | | Validation script, see above. |

The chunk-reference URIs in the JSON were rewritten to the relative
`data/…grib2` paths so the examples are portable within this directory. When you
generate your own manifest, the URI reflects the source location (a local
`file://` path, or the remote `s3://` / `https://` object you scanned).

To reproduce the round trip:

```bash
cd demos/kerchunk_fair_metadata
python -c "
import fsspec, xarray as xr, grib2io.codecs
fs = fsspec.filesystem('reference', fo='nam_references.json', remote_protocol='file')
ds = xr.open_dataset(fs.get_mapper(''), engine='zarr', consolidated=False)
print(ds)
print(ds.attrs)
"
```
